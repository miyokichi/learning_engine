# Learning Engine v0.3 使い方ガイド

## 何のためのツール？

Learning Engineは、仕事で使う判断基準を、人との会話から少しずつ記録する道具です。「以前の判断を今回も使えるか」「何が分からないか」を整理し、足りなければ質問します。間違いを訂正すると、過去の正しい判断を壊さないか確かめて例外条件を学びます。

自分で資料を取りに行ったり、設計を変更したりする道具ではありません。必要な情報と根拠は人が説明します。AIの推測は候補のまま保存され、確認なしで正式なルールにはなりません。

## インストールから最初の体験まで

Python 3.11以上とGitがあるWindows PowerShellで、次を順番に実行します。すでにclone済みなら、そのフォルダでvenvの行から始めてください。

```powershell
git clone https://github.com/miyokichi/learning_engine.git
cd learning_engine
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\learning-engine.exe --db tutorial.sqlite3 tutorial
```

各画面で内容を読み、進めるときは `確認` と入力します。Enterだけなら中断でき、同じコマンドで続きから再開できます。すべて架空の教材なので、自分の仕事のデータや承認は不要です。

仮想環境の有効化は不要です。以下でも `.venv` 内の実行ファイルを直接指定します。`--db` は `chat` や `tutorial` より前に書きます。

| 入口 | 使う場面 |
|---|---|
| tutorial | 最初に、質問・訂正・学習の仕組みを読む。LLM不要 |
| chat | 普段の仕事を自然な日本語で相談・報告する。自動解釈にはLLMが必要 |
| chat --sample | 決まった練習文だけを解釈する架空教材。LLM不要 |
| demo | 架空の回答・承認を自動投入し、詳細な結果をJSONで確認する |
| interact | 詳しい操作を番号と入力フォームで行う。LLMなしでも使える |

## LLMを設定する

ローカルのOllamaやLM Studio等でOpenAI互換APIを起動し、プロジェクトルートの `.env` を編集します。以下のポートは例です。使っているサーバーのポートと、実際に読み込んでいるモデル名を確認してください。

```dotenv
LE_LLM_URL=http://localhost:11434/v1
LE_LLM_MODEL=実際にサーバーで使用しているモデル名
LE_LLM_API_KEY=local
```

LM StudioのURL例は `http://localhost:1234/v1` です。別PCのサーバーなら、そのLAN内IPやホスト名を明示できます。`/chat/completions` はアプリが追加するので、URLには通常 `/v1` まで指定します。

設定の優先順位はCLI引数、環境変数、作業ディレクトリの `.env` の順です。別フォルダから起動するときは、`--env-file` をサブコマンドより前に指定します。

```powershell
.\.venv\Scripts\learning-engine.exe --db my_learning.sqlite3 doctor
.\.venv\Scripts\learning-engine.exe --db my_learning.sqlite3 chat
```

doctorは通常、通信せずにDBと設定を確認します。疎通も確認したい場合だけ `doctor --check-llm` を実行してください。架空の確認メッセージだけを送ります。

LLM未設定なら自然言語の自動解釈はできません。chatの入力原文は保存されますが、tutorialやinteractを使って操作してください。

## 普通に話しかける

「新しい案件で、前の計算モデルを再利用できるか確認したい。材料はAだが、形状が同じかは未確認です」のように話します。

AIは、目的と属性の解釈を表示します。正しければ `確認`、違えば「材料はBです。そこを修正して」と文章で説明してください。`OK` や「そうですね」は承認になりません。

必要条件が分からない場合、何をなぜ聞いているかと、回答で何が変わるかを表示します。確認していなければ「未確認」と答えます。Unknownを勝手にfalseへ変えません。同じ未確認の回答を繰り返し聞かず、新しい根拠が出るまで保持します。

初期DBにはルールがありません。REVIEWになったら「どの条件なら、どの結論になるか」を説明してください。例えば「材料がAなら再利用できる。材料を条件として覚えて」と話し、解釈・固定条件・回帰結果を確認します。数値2例からの境界の自動推定はしません。

## 画像を見ながら質問・ナレッジを蓄積する

画像入力に対応したモデル（Vision対応）を `.env` の `LE_LLM_MODEL` に設定し、`chat` を起動します。LLMへのリクエストではtemperatureを指定せず、サーバー・モデルの既定値を使います。

チャットの `人間>` に次のように入力してください。空白を含むパスは引用符で囲めます。Windowsのパスもそのまま指定できます。

```text
/image "C:\work\断面 画像.png"
```

続く入力欄に「この断面を前回と比較して、モデルを再利用できるか検討したい」のように、画像の説明と判断したいことを入力します。説明を空にして送信した場合は、AIが目的などの不明点を質問します。画像から読み取れない材質・スケール・測定条件は推測で確定せず、質問に回答して補ってください。解釈が正しければ `確認`、違えば修正内容を文章で伝えます。画像を添付しただけでは知識は確定しません。

既存の案件では「画像の観察内容を覚えて」と伝えると、観察文と属性を確認対象として整理します。`確認` 後に出典画像に結び付けてナレッジに保存し、必要な追加質問を表示します。質問への回答も解釈を確認してから属性へ反映します。判断基準をルールとして公開したい場合は、従来どおり訂正・回帰検査・公開確認を使います。

対応形式はPNG・JPEG・WebP、1枚5 MiB以下です。`/image` は1回に1枚を添付します。追加の画像も同じコマンドで送れます。LLMには現在の案件に関連する直近4枚を送信し、それ以前の画像もDBに保持します。新しい案件に切り替える場合は目的を明示し、必要な画像を改めて添付してください。

画像本体・ファイル名・ハッシュ・発言との対応を会話と同じSQLiteに保存します。元ファイルを移動・削除しても、同じDBと会話から再開できます。API失敗時も画像を保持するので、接続設定を修正後に「再試行して」と入力できます。LLM未設定なら画像と原文の保存のみ行い、自動解析はしません。画像は設定したLLMサーバーに送信されるため、そのサーバーが画像入力に対応していることを確認してください。`chat --sample` は固定教材であり、実画像の解析はしません。

## 状態と結論の違い

| 表示 | 意味 | 次にすること |
|---|---|---|
| ASK | 判断に必要な情報や確認が不足 | 質問に根拠付きで回答する。分からなければ未確認と伝える |
| REVIEW | ルール不足・競合・専門家レビューが必要 | 判断理由、訂正、追加検証を相談する |
| EXPLORE | 不確かさを残し、安全な内部調査案を検討できる | 仮定や調査方針を見直す。外部操作は実行しない |
| EXECUTE | 固定条件に基づき内部の判断を進められる | 結論と根拠を確認する。外部実行の許可ではない |
| BLOCK | 条件によって進めない | 禁止条件や根拠を専門家と見直す |
| REUSE_MODEL等 | 仕事上の結論 | 上の状態とは別。結論と、その根拠を確認する |

## 判断を訂正して教える

「そこは違います。断面を見直すと形状が異なりました。従来モデルをそのまま使わず再検証が必要です」のように話してください。

AIは直前の判断と、同じ親ルールにつながる承認済み過去事例を比較します。重要な違いを言葉で指定し、訂正の一文解釈を確認します。無関係な事例から例外を作ることは拒否します。

解釈を確認するとルールの草案を作り、回帰結果を示します。公開には、さらに別の `確認` が必要です。過去の正解を壊す場合は公開できません。違いを追加で確認し、草案を見直してください。

## 作業の進め方を教える

次のように、最初の発言を作業報告にしても構いません。

> 今日は断面画像を比較してから形状計算をしました。側壁形状が違ったためです。計算だけでは根拠が足りず、最終判断は保留しました。

AIは目的・実施条件・作業・理由・観察・結果・分岐・終了条件を候補として整理します。「どんな結果なら計算を省略できるか」などの不足事項を最大2件ずつ質問します。追加の報告も文章で伝えられます。

原文の解釈を `確認` し、続いて参考手順としての承認を `確認` します。操作ログを記録する仕組みをPCやツールへ埋め込む必要はありません。行った順番は観測順序であり、いつも必須の順序とは限りません。手順は自動実行しません。判断条件をルールにしたい場合は、改めて訂正・ルール候補として確認します。

## 新しい概念・足りない条件が見つかったら

「底部の丸まりも影響するかもしれない」のような情報は、未検証の概念・仮説候補として扱います。正式な属性にするには、定義・測り方・単位・適用範囲を確認します。過去の値を推測して埋めません。重要な概念なら、古い案件の再確認が必要になる場合があります。

質問候補の重要性をLLMが提案しても、それは仮説です。候補のままでは既存の正式ルールを書き換えません。

## 保存場所と再開

`--db my_learning.sqlite3` は、現在のフォルダにあるSQLiteファイルを使う指定です。同じファイルを使えばCase・判断・質問・原文・候補・確認・会話の続きが残ります。別のDB名なら独立した知識になります。

chatは `/exit` で終了します。同じコマンドで起動すると前回の会話を番号で選べます。確認待ちの対象や質問が復元されます。詳しい利用では、画面に表示された会話IDを `chat --session` に指定しても再開できます。`/status` で確認対象を見直せます。

教材の `tutorial.sqlite3` と自分の `my_learning.sqlite3` は分けてください。DBを共有・移行する前はアプリを終了してバックアップします。v0.2 DBを開くと会話等のテーブルを追加し、元のCaseや監査は保持します。

## 実際の短い操作記録

次は架空の固定教材の出力から、ID等を省略した抜粋です。自由な推論の実演ではありません。

```text
人間> 別の案件です。材料はA、形状の同等性は未確認です。
AI> 案件の候補を整理しました。
人間> 確認
AI> 案件の解釈を確認して保存しました。
判断：REUSE_MODEL / 状態：ASK
人間> 断面を見たら同じでした。
AI> 確認対象：回答の解釈
人間> 確認
AI> 回答の解釈を確認しました。
判断：REUSE_MODEL / 状態：EXECUTE
```

業務結論がREUSE_MODELでも、未確認の重要な候補条件があれば会話上はASKとして保留します。根拠ルールと、候補が未検証である説明も表示します。全手順は [TUTORIAL_ja.md](TUTORIAL_ja.md) にあります。

## 次に試すこと

1. tutorialで、質問・訂正・例外の意味を確認する。
2. chatで自分の作業を一件報告し、解釈を確認する。
3. 次の案件について判断を依頼し、不足条件に回答する。
4. 間違いがあれば理由と違いを説明し、草案と回帰結果を確認する。
5. `replay-experiment` の架空実験で、学習前後と保留の違いを見る。
